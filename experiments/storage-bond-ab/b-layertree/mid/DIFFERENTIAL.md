# Pinned LayerTree MID vs funded FROST: executable authority differential

Research track: `blossom-storage-bonds` draft PR #5, not a production
vault, not real Filecoin fault finality, and not a Bitcoin covenant.

## What is executed

One CI job checks out **both** codebases:

- `patrickdugan/sapio@34363851a11d0f2b3ddb27c050537c1a2e5b7e9b`
  supplies the original compiled experimental MID WASM guest, Bitcoin
  oracle wrapper, 60k/40k owner exits, four real integration tests,
  and persisted lineage reservation logic.
- This repository supplies `mid/sapio_mid_exit_vectors.rs`, copied into
  the pinned checkout's `integration_tests/examples/` only in the disposable
  runner. It constructs and executes two separate oracle-signed exits against
  the pinned guest, exports actual signed transaction hex, BIP341 witness
  transaction IDs and Merkle-sum roots. It does not edit the pinned
  library's contract implementation.
- `mid/verify_mid_vectors.mjs` independently checks the root hash/enc64
  serialization, wtxids against complete signed witness bytes,
  100k -> 40k -> 0 principal, independent 60k/40k beneficiary scripts,
  and Bob's parent transaction spending Alice's MID successor outpoint.
- The same job executes the real BIP341 2-of-3 FROST P2TR regtest with
  disposable Bitcoin Core 30.3 (SHA-256 pinned), including external
  fee sponsorship, genuine two-person Schnorr aggregation and separate
  Bitcoin-confirmed Alice/Bob wallet redemptions.
- `mid/compare_mid_frost.mjs` audits those two results together and emits
  a self-contained, **explicitly non-equivalent** authorization receipt.

## Real cryptographic distinction

| Check | Sapio MID guest | Funded FROST Bitcoin keypath |
| --- | --- | --- |
| Starting principal | 100,000 sats | 100,000 sats |
| Alice/Bob exit | Sequential 60k then 40k | One 60k/40k release |
| State evolution | Actual Merkle-sum 100k -> 40k -> 0 | Ad-hoc state commitment in OP_RETURN |
| Owner authorization | Alice/Bob individual signatures, plus online oracle | Threshold keypath signature |
| Settlement bytes | Oracle-signed synthetic fixture prevouts, **not mined** | Actually Bitcoin-confirmed |
| Misstated payout | Pinned guest rejects re-signed mutation | Two FROST shares can sign unauthorized payout |
| Altered opaque state commitment | Guest transition checks actual root | Bitcoin accepts freshly FROST-signed alternative with **unchanged 60k/40k outputs** |
| Outage before release | No oracle-free MID EXIT shown | No holder-only P2TR carrier exit shown |
| After payout | Payout records in MID synthetic guest | Each separately keys and confirms own real Bitcoin spend |

The current FROST P2TR script differs from Sapio's actual compiled MID
wrapper script. MID beneficiaries' P2TR exit-key scripts also differ from
the Bitcoin Core wallets' settlement scripts. Therefore their 60k/40k
amounts being equal does **not** demonstrate a common output commitment,
cryptographically bound MID guest verdict or restrictive spend policy.

The FROST keypath's Bitcoin consensus predicate is effectively
`VerifyBIP340(tweaked_group_key, actual_BIP341_sighash, aggregate_signature)`.
The native Bitcoin VM is not evaluating the MID guest. Merely signing
an OP_RETURN commitment, even one matching a legitimate state root,
cannot restrict a malicious 2-share quorum from signing a different
root, outputs or recipient. The MID guest is protected by its oracle
software; the FROST carrier is protected by **the threshold quorum**.

## Security and controls

All keys here are ephemeral and disposable. The Sapio witness example
uses fixed public test seeds from its pinned test fixture; the FROST
shares are generated by a one-process trusted dealer. Do not reuse
either set of keys with real funds. MID oracle and B FROST signer
are independent signing systems in this experiment.

The differential enforces `bitcoinConsensusEnforcesMid=false`,
`samePhysicalBitcoinCarrier=false`,
`offlineHolderRecoveryWithoutOracleOrFederation=false`,
`comparableFeeOrSecurityWinner=false` and
`storagePdpEvidenceBoundToMidRoot=false`. The Blossom source PDP hash
matches the reference evidence included in the separate FROST receipt,
but it is not cryptographically incorporated into the pinned MID root.

## Next engineering gate

An implementation that enforces LayerTree entitlement against a
malicious threshold must produce an **actual Bitcoin-invalid**
unauthorized spend, not merely a MID guest that declines to sign.
Options include an audited NUMS/hidden-keypath spend construction with
consensus-admissible restrictive leaves, or pre-signed, fully bound
holder exit transactions that remain independently broadcastable when
the entire oracle/FROST federation vanishes. Both approaches require
exact predecessor/successor outpoints, refresh ancestry, fee sponsorship,
owner payout scripts, anti-replay history, and testnet validation.

The work remains upstream of any permissionless Filecoin-on-Bitcoin
adjudication claim. A Filecoin chain finality verifier and absence proof
are additional unresolved dependencies.
